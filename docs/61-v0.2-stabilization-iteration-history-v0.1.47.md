# v0.2 Stabilization: Iteration History & Contract Audit — v0.1.47-alpha

`v0.1.47-alpha` начинает стабилизационный этап перед `v0.2`. Релиз не вводит новый runtime и не объявляет `v1beta1`; он закрывает долг модели состояния `loop_group`, фиксирует границы будущего стабильного API и устраняет остаточные обходы persistence redaction из ревью `v0.1.46`.

## First-class iteration history

`NodeState` для `loop_group` теперь хранит два совместимых представления:

- `loop_previous` — прежний публичный snapshot последней завершённой итерации;
- `loop_iterations[]` — полная история всех завершённых итераций текущего Run.

Каждый элемент `loop_iterations` содержит:

```json
{
  "iteration": 2,
  "nodes": {},
  "until_node": "check",
  "exit_code": 0,
  "status": "completed",
  "satisfied": true,
  "completed_at": "..."
}
```

История является durable state: она переживает reload/resume, проходит через общий redaction и доступна через обычный state/MCP `run.get`. Внутренние expanded IDs фильтруются в `PublicView`, как и для `loop_previous`.

Для ограничения размера durable state `loop_group.max_iterations` теперь имеет явный максимум `64`. Dynamic Plan уже имеет более строгие собственные бюджеты; лимит 64 относится к статическому Workflow contract.

`loop_previous` не удаляется в `v0.2`: это compatibility alias последней итерации. Для старых Run, созданных до `v0.1.47`, Takt не выдумывает отсутствующую историю; доступен сохранённый `loop_previous`, а `loop_iterations` заполняется для новых завершённых итераций после обновления.

## Решение по nested composition

В `v0.2` вложенный `loop_group` остаётся запрещённым. `subworkflow`, `foreach`, governed `workflow` и approval внутри `loop_group` поддерживаются и используют существующий path namespace.

Причина решения — не техническая невозможность, а отсутствие evidence, что произвольная рекурсивная loop-композиция оправдывает дополнительную сложность resume/state/evidence contract. Возможность можно вернуть после production-evals как отдельное совместимое расширение.

## Contract audit перед v1beta1

### Stable-candidate

Эти контракты сохраняются как основа `v0.2` и являются кандидатами на будущий `v1beta1`:

- `takt/v1alpha1 Workflow` и базовые node semantics;
- Config/Profile/BlockPackage loading и deterministic fingerprints;
- durable Run lifecycle, events и typed artifacts как наблюдаемый control contract;
- пять public agent tools `takt.task.*`;
- neutral SCM/Tracker/CI operation model;
- package lock/source/integrity semantics.

Статус stable-candidate не означает немедленную смену `apiVersion`: `v0.2` продолжает читать текущие `v1alpha1` документы.

### Supported alpha

Остаются поддерживаемыми, но пока не замораживаются в `v1beta1`:

- TaskRoute и bounded `WorkflowPlan`;
- task/workflow evaluation matrix/report formats;
- Agent Adapter SDK и Domain Adapter SDK;
- Pi/OpenCode host-control adapters до live strict conformance;
- MCP host/worker/operator surfaces;
- Dynamic Plan promotion format.

Их можно уточнять по production evidence без миграции основного Workflow DSL.

### Deprecated

`takt-assistant/v1alpha1` остаётся читаемым ради совместимости старых process wrappers, но новым wrappers следует использовать `takt-assistant/v1alpha2` и conformance kit. Срок удаления не фиксируется до появления хотя бы одного production external wrapper и compatibility matrix.

### Internal

Не являются стабильным пользовательским API:

- файловая раскладка `.takt/runs`, `.takt/plans`, locks и daemon socket;
- expanded/internal node IDs;
- implementation-specific store commit protocol;
- generated host/session helper state;
- fake adapters и deterministic benchmark fixtures.

Пользовательский или корпоративный код не должен зависеть от этих деталей напрямую.

## Draft migration policy `v1alpha1 → v1beta1`

`v1beta1` будет вводиться только после P0 production evidence. До этого действуют правила:

1. `v0.2` продолжает принимать `takt/v1alpha1` Workflow/Config/Package.
2. Additive state fields (`loop_iterations`, diagnostics, sandbox decisions) не требуют миграции definition files.
3. `loop_previous` сохраняется как compatibility field как минимум на всём этапе `v0.2`.
4. Любое удаление или переименование authoring fields требует отдельного migration command/guide и regression fixtures.
5. Public agent MCP surface не расширяется только ради внутренних возможностей runtime.
6. Provider-specific возможности остаются за Adapter SDK и capability discovery.

Финальная таблица field-by-field migration появится после live Route DSL + Go + Document evidence, когда станет видно, какие experimental controls действительно используются.

## Security fixes from v0.1.46 review

- control persistence redactor строится из `RunState.config_path`, поэтому profile-resolved и per-run config override регистрируют правильные `secret://` refs;
- runtime и control используют один constructor регистрации config secrets;
- evaluation approval path коммитит redacted clone вместо live state;
- validation report, записываемый через `output_path`, редактируется до записи;
- оставшиеся прямые Run-state commits в control operations переведены на общий redacted commit helper;
- production-записи `WorkflowPlan` из control проходят redaction по `record.config_path`, поэтому results/steering/errors не образуют отдельный persistence bypass.

## Task evaluation fixes

- `min_plan_revisions: 1` означает только initial plan и не входит в denominator replan expectation; replan ожидается начиная с `2`;
- `needs_input` вычисляется по durable plan после reload;
- `final_success=true` больше не сохраняется одновременно с `error`;
- repeat>1 проверяется E2E структурированными Go-assertions;
- workspace fingerprint и copy используют один runtime-directory exclusion contract;
- task/evaluation report schemas получили типизированные nested records вместо свободных `object`.

## Verification

К релизному gate добавлен `scripts/test-iteration-history.sh`, который проверяет:

- три завершённые итерации в durable/public state;
- `satisfied=false,false,true`;
- совместимость `loop_previous`;
- fail-closed `max_iterations > 64`.
