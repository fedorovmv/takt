# Усиление композиции workflow в v0.1.23-alpha

## Назначение среза

Срез синхронизирует код, схемы, документацию и релизные проверки после ревью v0.1.22-alpha. Архитектурный инвариант сохранён: композиция компилируется в обычный DAG до `Validate`, а runtime использует один scheduler и один Run.

## Исправления ревью

### Воспроизводимость проверок

`TEST_RESULTS.md` теперь содержит фактически выполненные команды, сведения о среде и отдельный раздел известных нестабильных тестов. Два timeout/overflow-теста получили реалистичный запас времени и отдельно прогоняются несколько раз. Pi adapter игнорирует штатный `os.ErrClosed` от stderr pipe после завершения процесса; это устраняет ложную protocol-классификацию `process_exit`. Релизный отчёт не объявляет команду успешной, если она завершилась по внешнему лимиту или не запускалась.

### Согласование схемы и кода

Для композиционного контейнера схема повторяет value-семантику валидатора: `attempts.max: 0`, пустые hooks и timeout, а также `allow_failure: false` эквивалентны отсутствию поля. Значимые групповые policies остаются внутри дочернего workflow.

`assistant`, `model` и `session` разрешены на контейнере и становятся defaults подключённого вызова. Явные поля дочернего узла имеют больший приоритет.

### Поля, ошибки и команды

Документация перечисляет `session` и `native_hooks`, фиксирует предел глубины 16 и пользовательские ошибки рекурсии. Проверки покрывают превышение глубины, запрещённые значения контейнера и неразрешённые `${inputs.<name>}`.

Локальная Markdown-команда ищется рядом с подключённым workflow и далее вверх до корня композиции. Это включает структуру профиля `workflows/*.yaml` + `commands/*.md`. Содержимое команды остаётся частью fingerprint.

Проверка результата `resolveInputs` выполняется до обработки карты. Переписывание ссылок в prompt/bash затрагивает только `${nodes.<id>...}` и `${loop.previous.<id>...}`; голый текст `nodes.id.` сохраняется. В `when` голая форма по-прежнему поддерживается как выражение.

## Расширение композиции

### Внешний список foreach

`foreach` принимает ровно один источник:

```yaml
foreach:
  items: [lint, test]
```

или:

```yaml
foreach:
  items_from:
    path: checks.yaml
```

`items_from.path` вычисляется относительно содержащего workflow. YAML/JSON-файл должен содержать непустой массив верхнего уровня. SHA-256 исходных байтов включён в скомпилированное определение, поэтому изменение списка блокирует resume старого Run.

### Композиция внутри loop_group

`subworkflow` и `foreach` разрешены в дочернем DAG `loop_group`. Они проходят тот же этап компиляции, что и корневые узлы. `until.node` продолжает ссылаться на публичный ID контейнера. Approval и вложенный `loop_group` внутри цикла остаются запрещены.

### Результат foreach

Публичный output `foreach` содержит JSON-массив результатов всех итераций в исходном порядке. Результат, являющийся корректным JSON, сохраняет тип; обычный текст записывается строкой.

### Публичная проекция Run

Полное состояние с namespaced ID сохраняется в `state.json`, поскольку оно необходимо для resume, fingerprint-проверки и точной диагностики. Команды CLI `run`, `status`, `answer` и `resume` возвращают публичную проекцию:

- внутренние узлы с `__` скрыты;
- `current_node` и `waiting.node_id` отображаются через ID контейнера;
- approval внутри subworkflow принимается через публичный ID контейнера;
- внутри `loop_previous` остаются только публичные дочерние узлы.

## Оставшиеся ограничения

- `foreach` выполняется последовательно;
- `attempts`, `timeout`, hooks, `native_hooks` и `allow_failure` для всей композиционной группы требуют отдельной scheduler-семантики и задаются внутри дочернего workflow;
- полный сохранённый `state.json` содержит внутренние ID, а стабильным внешним контрактом является публичная проекция CLI;
- approval и вложенный `loop_group` внутри `loop_group` остаются запрещены.
