# Подход к решению

## Основное решение

Реализация создаётся как новый Go-проект, а Archon используется как поведенческая спецификация и источник проверенных концепций. Прямой перенос TypeScript-кода не выполняется.

## Почему новый runtime

Прямой порт Archon потребовал бы переносить сервер, web UI, каналы интеграции, GitHub-функции, фоновые задания и другие продуктовые части. Они не нужны для проверки основной гипотезы и значительно увеличивают стоимость разработки.

Полностью самостоятельное проектирование также рискованно: команда повторит эволюцию от последовательных шагов к DAG, циклам, approval, hooks и каталогам команд.

Выбранный путь:

```text
совместимое по смыслу подмножество Archon
→ собственная строгая схема
→ компактный Go-runtime
→ тесты поведения
→ постепенное расширение
```

## Архитектурные границы

### Workflow runtime

Отвечает за DAG, условия, циклы, retries, approval, hooks, состояние и события.

### Assistant adapter

Запускает готовый кодовый агент. Runtime передаёт ему инструкцию, модель, рабочий каталог, режим сессии и метаданные.

### Model catalog

Хранит логические имена моделей и параметры. Workflow не обязан содержать реальные идентификаторы моделей.

### Command library

Хранит переиспользуемые Markdown-инструкции. Команда определяет поведение агента, но не является отдельной фиксированной ролью.

### Portable hooks

Запускаются runtime до или после узла и работают с любым исполнителем.

### Native hooks

Спецификация предусматривает непрозрачную конфигурацию внутренних hooks конкретного агента. Базовая реализация передаёт её адаптеру как метаданные, но не интерпретирует.

## Смена гипотез без изменения кода

Конфигурацией должны меняться:

- число и последовательность агентных узлов;
- инструкции;
- модели;
- исполнители;
- общий или свежий контекст;
- проверки;
- поведение после ошибки;
- число попыток;
- одиночный или групповой цикл;
- точки approval.
