# Целевое состояние Takt v0.2

## 1. Назначение версии

Takt v0.2 должен подтвердить основную архитектурную гипотезу проекта: один runtime способен воспроизводимо выполнять разные агентные процессы, а изменение стратегии требует правки workflow, Markdown-команд и конфигурации моделей, но не ядра Go.

Версия считается успешной, если через один и тот же runtime работают три несвязанных сценария:

1. генерация и исправление Route DSL;
2. исправление ошибки в Go-проекте;
3. подготовка технического документа с согласованием.

## 2. Граница продукта

Takt v0.2 отвечает за:

- загрузку и проверку workflow;
- выбор логической модели и внешнего исполнителя;
- выполнение DAG;
- одиночные и групповые циклы;
- переносимые hooks;
- передачу обратной связи в новую или продолженную агентную сессию;
- approval с сохранением и продолжением запуска;
- состояние, события, артефакты и метрики запуска;
- машинный CLI.

Takt v0.2 не реализует:

- собственный tool-calling цикл;
- файловые инструменты для LLM;
- MCP-клиент внутри агентной сессии;
- LSP, память проекта и субагентов;
- Web UI, многопользовательский сервер и удалённых workers.

Эти функции остаются у Pi, OpenCode и других внешних исполнителей.

## 3. Обязательные возможности

### 3.1. Модели

- логические имена моделей в `Config`;
- отдельные provider, model ID и параметры;
- выбор модели на уровне defaults, Markdown-команды и узла;
- приоритет: узел → команда → workflow defaults;
- передача всех параметров адаптеру без потери данных;
- фиксация разрешённой модели в журнале запуска.

### 3.2. Исполнители

Минимум один реальный адаптер — Pi или OpenCode — должен пройти интеграционные тесты.

Адаптер обязан поддерживать:

- рабочий каталог;
- prompt через stdin или аргумент;
- выбранную модель;
- тайм-аут и отмену;
- нормализованный stdout, stderr и exit code;
- идентификатор сессии, если исполнитель его предоставляет;
- режимы `fresh` и `resume`;
- декларацию возможностей.

### 3.3. Markdown-команды

- project, workflow-local и user scope;
- frontmatter с assistant, model и metadata;
- шаблоны входа, feedback, outputs и approval;
- запуск отдельно через `takt command run`;
- одинаковая семантика при отдельном запуске и внутри workflow.

### 3.4. DAG

- `depends_on`;
- `when`;
- `trigger_rule`;
- детерминированный порядок для готовых узлов;
- параллельное выполнение независимых узлов можно отложить до следующей версии;
- статическая проверка ссылок, циклов и возможностей исполнителя.

### 3.5. Циклы

Нужны два механизма:

1. повтор отдельного узла через `attempts` и hooks;
2. повтор подграфа через `loop_group`.

Для `loop_group` обязательны:

- `max_iterations`;
- детерминированное условие `until`;
- результаты текущей и предыдущей итерации;
- fresh/resume policy для агентных узлов;
- понятное состояние при исчерпании итераций.

### 3.6. Hooks

Переносимые hooks:

- `before_node`;
- `after_node`;
- `before_complete`;
- `on_failure`.

Решения hooks:

- `continue`;
- `retry`;
- `fail`.

Hook должен возвращать нормализованную обратную связь. При `retry` она передаётся следующей попытке через `${feedback}`.

Native hooks допускаются только как capability конкретного адаптера. Runtime хранит и передаёт их, но не имитирует неподдерживаемую семантику.

### 3.7. Approval

- Run переходит в `waiting`;
- состояние записывается до возврата CLI;
- ожидание не расходует попытку;
- ответ принимается отдельной командой;
- продолжение возможно из нового процесса CLI;
- повторный ответ на завершённый или другой approval отклоняется;
- ответ доступен как `${approvals.<node-id>}`.

### 3.8. Состояние и события

Каждый Run хранит:

- снимок состояния;
- append-only журнал событий;
- каталог артефактов;
- разрешённые workflow, config, models и assistants;
- длительность, попытки и результаты узлов.

Для v0.2 допустимо файловое хранилище. Запись состояния должна быть атомарной.

### 3.9. Машинный интерфейс

CLI должен поддерживать JSON для всех операций:

```text
takt validate
takt run
takt answer
takt status
takt cancel
takt command run
```

Команда `cancel` входит в целевой объём v0.2, даже если отсутствует в текущем прототипе.

## 4. Сквозные критерии приёмки

### Route DSL

- агент создаёт или изменяет `route.yaml`;
- внешний валидатор обнаруживает ошибку;
- диагностические данные попадают в `${feedback}`;
- агент исправляет текущий файл;
- детерминированная проверка завершает цикл;
- Run останавливается на approval и продолжается отдельной командой.

### Go-проект

- агент получает описание ошибки;
- изменяет исходный код;
- `go test ./...` используется как внешний hook или узел;
- процесс повторяется до успешных тестов либо лимита попыток.

### Документ

- один узел готовит черновик;
- approval возвращает комментарий;
- следующий узел перерабатывает документ;
- итоговый файл регистрируется как артефакт.

## 5. Нефункциональные требования

- Go 1.23+;
- `context.Context` проходит через runtime и адаптеры;
- дочерние процессы завершаются при отмене контекста;
- неизвестные поля конфигурации вызывают ошибку;
- ошибки содержат Run ID, Node ID и причину;
- один workflow можно повторно запустить без ручной очистки состояния;
- секреты не записываются в события и state;
- stdout/stderr имеют настраиваемый лимит;
- путь записи артефактов ограничен workspace.

## 6. Что не блокирует v0.2

- параллельный scheduler;
- CEL;
- SQLite;
- восстановление исключительно по event log;
- MCP-сервер;
- Web UI;
- worktree isolation;
- marketplace пакетов.

## 7. Условие перехода к v1beta1

Переход к более стабильной схеме возможен после выполнения трёх сквозных сценариев и как минимум десяти реальных запусков каждого сценария. По результатам фиксируются:

- стабильная семантика session policy;
- формат capabilities;
- модель ошибок;
- область видимости данных внутри циклов;
- схема событий;
- минимальный контракт артефактов.
